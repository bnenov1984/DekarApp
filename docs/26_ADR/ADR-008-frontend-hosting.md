# ADR-008 — Frontend хостинг: Render Static Site

**Статус:** Accepted (Engineering, 2026-10-06)
**Отговаря на:** "Къде се хоства SPA-то?" — ADR-007 реши хостинга само за новия backend (`areaflow-api`); SPA-то беше насочено към GitHub Pages (`npm run deploy` + `gh-pages`), което никога не е деплойвано и не е достъпно за private repo на безплатен GitHub план.

## Контекст

- SPA-то е чист статичен build (Vite → `dist-ui/`, ADR-006) — без сървърен рендеринг и без URL routing (2 екрана + overlays), следователно не са нужни rewrite правила.
- PD-022/PD-023: desktop-first, cloud-first данни с режим гост; без service worker и без PWA инсталируемост. Хостингът не трябва да носи нищо повече от статични файлове.
- Нужда сега: PO да тества и ползва продукта, докато разработката продължава — всеки merge в `main` трябва да стига до живата версия без ръчна стъпка.
- Guardrail „простота" и „избягвай ненужни инфраструктурни разходи" (ADR-007) важат и тук.

## Решение

**Хостинг: Render Static Site**, описан като код в `render.yaml` (Render Blueprint) в корена на репото:
- build `npm ci && npm run build`, публикува `dist-ui/`, Node 24;
- автоматичен деплой при push в `main`, **само след като GitHub CI проверките минат** (`.github/workflows/ci.yml`);
- Vite `base: '/'` — приложението се сервира от корена на домейна.

**Допълнение (ADR-009, 2026-11-15, по PD-026):** коренът на сайта е публичната начална страница; SPA-то се сервира от `/app/`. `base: '/'` остава.

GitHub Pages деплоят (`deploy` скриптът и `gh-pages` пакетът) се премахва.

### Защо Render

- Същият vendor като backend-а (ADR-007): един акаунт, едно табло, една сметка — по-малко операционна повърхност за solo/AI-assisted екип (същата обосновка като ADR-006/007).
- Безплатните статични сайтове се сервират от CDN, не „заспиват" и позволяват комерсиална употреба — няма да се налага миграция при старта на плащанията.
- Конфигурацията е в репото (`render.yaml`), не само в таблото.

## Отхвърлени алтернативи

| Опция | Защо не |
|-------|---------|
| **GitHub Pages** | Изисква публично repo или платен GitHub план; сервира от под-път (`/AreaFlow/`), което усложнява `base`. |
| **Vercel (Hobby)** | Най-добрите preview-та, но безплатният план е само за некомерсиална употреба — миграция при старта на плащанията. Разумен избор, ако preview-тата станат важни. |
| **Cloudflare Pages** | Почти равностойна (безплатна комерсиална употреба, R2 вече е в Cloudflare по ADR-007); губи само по „един vendor с backend-а". Естествен fallback. |
| **Netlify** | Равностойна по възможности; няма предимство пред Render при този мащаб. |

## Последици

- **Домейн и локални данни.** IndexedDB (ADR-004; гост-проектите по PD-023) е обвързан с домейна. Тестването на `*.onrender.com` е приемливо, но преди реални потребители продуктът минава на собствен домейн — иначе локалните им проекти остават на стария адрес при смяната.
- **Cookies с backend-а (когато `areaflow-api` бъде деплойнат).** `onrender.com` е в Public Suffix List, така че `areaflow.onrender.com` и `areaflow-api.onrender.com` са различни сайтове и Safari блокира сесийния cookie. Изискване към деплоя на backend-а: собствен домейн с поддомейни (`app.` / `api.`) **или** rewrite в `render.yaml`, който препраща `/api/*` и `/v1/*` към backend-а, така че браузърът вижда един домейн. До тогава вход/„Save to account" на живата версия не работят — останалото приложение работи изцяло (`VITE_AUTH_API_URL` не е зададен; адаптерите връщат `NETWORK_ERROR`, не crash).
- `npm run dev` вече сервира на `http://localhost:5174/` (без `/areaflow/`).
- `docs/INDEX.md` §6 получава ред „frontend hosting → ADR-008".

## Отворено за следваща задача

Собственият домейн (кога и кой), деплоят на `areaflow-api` (Render Web Service + Neon, ADR-007) и изборът между поддомейни и rewrite за cookies.
